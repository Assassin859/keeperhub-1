## High-severity findings on the new code

### 1. `safe_fetch_blocks_alert` may never receive data
`lib/safe-fetch.ts:324` calls `metrics.incrementCounter("safe_fetch.blocks.total", ...)`. The metric is **not** registered in `lib/metrics/collectors/prometheus.ts:counterMap` (lines 1003–1018). When the Prometheus collector is called with an unknown name, it logs `[Prometheus] Unknown counter metric: safe_fetch.blocks.total` and skips the increment. The Grafana query I added (`safe_fetch_blocks_total{shadow="false"}`) will sit at `no_data` forever.

Need to register a Counter (name `keeperhub_safe_fetch_blocks_total`, labels `reason, plugin_name, shadow`) and wire it into `counterMap`. Fixing now.

### 2. Behavioral cron has no scheduler
`/api/cron/security-behavioral-scan` is defined but **nothing invokes it**. The Loki rule for `security.behavioral.new_account_first_workflow` will never fire because no log line is emitted. The PR description calls this out as a follow-up, but it's worth being explicit: the behavioral alert is **shipped but inert** until a K8s CronJob in `techops_infrastructure` (similar to whatever invokes `agentic-wallet-sweeper` every 5 min) is added.

### 3. Cron endpoint name is misleading
The endpoint is called `security-behavioral-scan` and emits an event named `new_account_first_workflow`, but the query doesn't actually identify the *first* workflow per user — it surfaces ANY execution by a new account in the last 5 minutes. A new user running a benign demo workflow that then triggers 5 quick re-runs (e.g., debugging) will produce 5 events. Two reasonable fixes:
- Rename to `new_account_workflow_attempt` so the name matches the query
- Add a Postgres anti-join to filter to first-only (`AND NOT EXISTS (SELECT 1 FROM workflow_executions e2 WHERE e2.user_id = ... AND e2.started_at < e.started_at)`)

The first option is simpler and preserves the signal (we want every new-account workflow surfaced for triage, not just the first).

## Medium-severity findings

### 4. Auth bypass via `NODE_ENV=test` reads from process env on every request
`isAuthorized()` returns true unconditionally when `NODE_ENV` is `"development"` or `"test"`. If the staging container ever boots with `NODE_ENV=test` (misconfiguration or test container reuse), the endpoint becomes openly callable. Tightening: require BOTH (`NODE_ENV in {development, test}`) **AND** (`!CRON_SECRET`) for the bypass — if a secret is set, always check it regardless of env. One-line fix.

### 5. Cron endpoint has no rate limit
A leaked URL or load-balancer log entry lets anyone trigger an unauthenticated 401 path repeatedly — minimal risk, but auth-then-query is at least a DB query per call when CRON_SECRET is exposed. Existing repo pattern in `lib/mcp/rate-limit.ts:getClientIp` + an IP bucket would cover it.

### 6. Cron emits stdout-only, not Sentry
All other security captures (`deactivated_login_attempt`, `backstop_execution_blocked`, `content_scanner_hit`) dual-emit to Sentry + stdout. The new `new_account_first_workflow` event is stdout-only. For consistency with the existing alert plane, add the `captureMessage` mirror.

### 7. Behavioral query uses `sql\`${users.id} = ${workflowExecutions.userId}\`` for join
Functional, but the idiomatic Drizzle form is `eq(users.id, workflowExecutions.userId)`. Cosmetic; one-line swap.
